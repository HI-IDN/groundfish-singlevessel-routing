Sweep Matheuristic for Groundfish Survey Routing
==================================================

Overview
--------

The sweep stage implements a parameter-sweep matheuristic that iteratively improves a solution by varying the L2seg parameter and calling the capacity-aware MIP model. Starting from an initial solution (generated by the `init` stage), the sweep algorithm:

1. Takes an initial tour/ordering of stations
2. Partitions the tour into L2seg-length segments
3. For each segment, solves a capacity-aware MIP to optimize sub-tour
4. Records the objective value at each L2seg iteration
5. Returns the best solution found and full optimization trajectory

This approach allows efficient exploration of the solution space without exhaustively solving the full problem.

Algorithm
---------

### High-Level Pseudocode

```
Input: initial_solution, L2seg_values = [60, 120, 180, ...]
Output: best_solution, trajectory

best_solution ← initial_solution
trajectory ← []

for L2seg in L2seg_values:
    current_solution ← best_solution
    improved ← true
    iteration ← 0
    
    while improved and iteration < max_iterations:
        improved ← false
        iteration ← iteration + 1
        
        // Divide tour into overlapping segments of length L2seg
        for segment_start = 0 to len(tour) - L2seg step stride:
            segment_end ← segment_start + L2seg
            
            // Extract sub-problem: stations in segment + boundary depot
            sub_instance ← extract_subproblem(current_solution, segment_start, segment_end)
            
            // Solve sub-MIP with time limit
            sub_solution ← solve_mip_capacity_aware(sub_instance, time_limit)
            
            // Check if solution improved
            if sub_solution.objective < current_solution.objective:
                current_solution ← apply_sub_solution(current_solution, sub_solution)
                improved ← true
        
        // Log trajectory
        trajectory.append({
            L2seg: L2seg,
            iteration: iteration,
            objective: current_solution.objective,
            timestamp: now()
        })
    
    // Update best known solution
    if current_solution.objective < best_solution.objective:
        best_solution ← current_solution

return best_solution, trajectory
```

### Key Parameters

- **L2seg:** Segment length (number of stations per sub-MIP)
- **L2seg_min, L2seg_max, L2seg_step:** Range to sweep (e.g., 60, 480, 60 → [60, 120, 180, ...])
- **MIP time limit:** Maximum seconds per sub-MIP solve (typically 30–120 seconds)
- **Max iterations per L2seg:** Prevent infinite loops (default: 10)
- **Segment stride:** Step size for sliding window (default: L2seg / 2, for overlap)

CLI Usage
---------

### Basic Invocation

```bash
./bin/sweep \
  --db dat/parsed_data.sqlite \
  --init-solution init_nn.json \
  --l2seg-min 60 --l2seg-max 480 --l2seg-step 60 \
  --mip-time-limit 120 \
  --log-level info
```

### Arguments

- `--db <path>` — SQLite database (required)
- `--init-solution <path>` — Initial solution JSON from `init` stage (required)
- `--l2seg-min <n>` — Minimum L2seg value (default: 60)
- `--l2seg-max <n>` — Maximum L2seg value (default: 480)
- `--l2seg-step <n>` — L2seg increment (default: 60)
- `--mip-time-limit <seconds>` — Per-MIP time limit (default: 120)
- `--mip-threads <n>` — Gurobi thread count (default: auto)
- `--max-iterations <n>` — Max iterations per L2seg (default: 10)
- `--stride <n>` — Segment stride (default: L2seg / 2)
- `--log-level {debug|info|warn|error}` — Logging verbosity (default: info)
- `--save-to-db` — Insert results into SQLite `sweep_runs` table (optional)
- `--output {json|csv}` — Output format (default: json)

### Examples

**Default sweep over [60, 120, ..., 480] with 120-second time limit per MIP:**

Data Flow
---------

### Inputs

1. **Initial solution (JSON)** from `init` stage
   - Tour: ordered list of station IDs
   - Total distance
   - Metadata (strategy, runtime)

2. **SQLite database**
   - Distance matrix (computed from locations)
   - Feasibility matrix (land-crossing, capacity constraints)
   - Vessel capacity, station demands

3. **Parameters**
   - L2seg sweep range
   - MIP time limits
   - Iteration limits

### Processing

1. Load initial solution
2. For each L2seg value:
   - Divide tour into segments
   - For each segment, extract sub-problem
   - Solve sub-MIP (capacity-aware)
   - If improved, update tour
   - Log iteration
3. Track best solution and trajectory

### Outputs

1. **JSON/CSV trajectory** — All iterations and objective values
2. **Best solution** — Optimal tour found
3. **Improvement statistics** — % improvement vs. initial, vs. each L2seg
4. **SQLite `sweep_runs` table** (optional) — Persistent record of run

Segment Extraction
------------------

When extracting a segment from a tour:

```
Initial tour: [5, 12, 3, 45, 67, 89, 102, 120, ...]
L2seg: 3
Segment start: index 2

Segment nodes: [3, 45, 67]
Depot (start/end): port location (e.g., 5)

Sub-problem:
  - Nodes: [depot, 3, 45, 67]
  - Objective: minimize distance visiting 3, 45, 67 and returning to depot
  - Constraints: capacity, feasibility (as in full MIP)
```

Sub-MIP Solution Update
-----------------------

Once a sub-MIP is solved:

```
Original tour: [..., 3, 45, 67, 89, ...]
Sub-MIP tour: [depot, 45, 3, 67, depot]  (reordered)

Updated tour: [..., 45, 3, 67, 89, ...]
              (replace segment with optimized order)
```

Performance Considerations
---------------------------

1. **Segment overlap:** Set stride = L2seg / 2 for overlapping segments (improves solution but slower)
   - Stride = L2seg: non-overlapping (faster, less effective)
   - Stride < L2seg / 2: more overlap (slower, better solution potential)

2. **L2seg values:** Larger segments allow more complex optimization but increase MIP difficulty
   - L2seg = 30–60: fast MIP solves, limited reordering
   - L2seg = 120–240: moderate complexity
   - L2seg = 300+: slow, may hit time limits

3. **Time limits:** Adjust per MIP based on instance size and available compute
   - Small instance (n < 100): 30–60 seconds per MIP
   - Medium instance (n = 100–500): 60–180 seconds per MIP
   - Large instance (n > 500): 180–600 seconds per MIP

Troubleshooting
---------------

- **No improvement after multiple L2seg values:** Initial solution may be near-optimal; try increasing time limits or reducing L2seg.
- **MIP solver timeout frequently:** Reduce segment size (L2seg), increase time limit per MIP, or reduce thread count for deterministic behavior.
- **Memory exhaustion:** Large distance matrices may overflow memory. Reduce L2seg or use sparse matrix representation.
- **Divergent solutions:** Ensure feasibility matrix is correctly computed (land crossing constraints, capacity satisfaction).
